# Working with a Speckify-managed contract

This repo publishes an OpenAPI contract through Speckify. Speckify bundles
the spec, works out its own semver bump from what actually changed on the
wire, generates client/server packages, and publishes them when a pull
request merges. It changes how you should approach both the spec and any
generated code.

## Contract first

Change the OpenAPI spec before touching the implementation. The spec is
the source of truth: client and server packages, and their types, are
generated from it. Editing generated code instead of the spec is edited
away the next time the spec changes and the code is regenerated.

## Never type or bump a version

Do not edit `info.version` in the spec, and do not try to decide the next
version yourself — **`info.version` is ignored**. Speckify computes the
bump itself by diffing the newly bundled spec against whatever the
registry says was last published, judging the diff against an allow-list
of change shapes known to be safe for an existing client, and taking the
highest bump across several independent checks. Nothing you type into the
spec influences this.

## Preview the bump before you push

Run `speckify plan` locally to see what version this change would produce
and why, before opening a pull request. It bundles the spec, computes the
bump, and prints the changelog exactly as the PR comment will.

## Read the PR comment

Once a pull request is open, Speckify comments on it with the bump it
would publish for each contract (`previous → next (bump)`) and the
changelog behind it. Read that comment rather than guessing: it's driven
by the same computation `speckify plan` runs locally, against the
registry's live last-published state.

## Minor vs. major, in plain terms

- **Patch**: a documentation-only change (descriptions, examples, titles
  in `info`, and similar).
- **Minor**: an edit that matches a known-safe shape for an existing,
  correctly-written client — for example a new operation, a new optional
  parameter or property, or a relaxed request constraint.
- **Major**: everything else, however small it looks. Removing a field,
  narrowing a type, renaming an operation, or tightening a constraint are
  all major. **Major is fine when the change genuinely needs it** — the
  goal is an accurate bump, not a small one.

## Generated code is regenerated, never edited

Never hand-edit a generated client or server package. On the server side,
Speckify generates a typed `Handlers` interface (TypeScript) or Protocol
(Python) — one method per operation, with the request already parsed and
validated and the return type constrained to the response shapes the spec
declares. Implement that interface. When the spec changes and the code
regenerates, a handler that no longer matches the interface fails to
compile or type-check; let that failure guide the change rather than
patching the generated file.

## Lint refusals

Speckify lints the bundled spec before anything else runs. A few refusals
come up often enough to recognise on sight:

- **`operationId` collisions after normalisation.** Two operations whose
  IDs become the same identifier once case and separators are ignored
  would generate one function name in the SDKs; give them distinct IDs.
- **Parameter-name collisions.** Two parameters on the same operation that
  normalise to the same generated name collide as keyword arguments in
  the generated Python client; rename one.
- **`patternProperties`.** Every generator Speckify targets silently drops
  it. Use `additionalProperties: <schema>` instead.
- **Reserved Python model member names.** A property whose generated
  Python attribute name collides with a member the Python model template
  already defines on every generated class breaks at runtime; rename the
  property.
- **OpenAPI 3.0.x or 3.1.x only.** Any other `openapi` version is refused
  outright.

Each refusal's message names the exact location and what to rename or
change.
