How Speckify works

Speckify turns an OpenAPI contract, kept in the repository of the service that owns it, into versioned TypeScript and Python packages. Nobody picks the version: it is computed from what changed, and it is built so that a breaking change can never ship under a compatible version number. This page explains how, piece by piece, so you can trust the result without reading every line of code.

Design principles

The spec lives with its producer

A spec sits beside the routes that serve it. Speckify holds no specs; it is a tool each producing repository adopts with one config file and one workflow file.

Nobody types a version

The version is computed from the difference between the spec being published and the spec that was last published. info.version in the source is ignored.

Over-bump, never under-bump

When Speckify cannot prove a change is safe for existing clients, it calls it major. An unnecessary major costs a consumer an upgrade decision; a missed one breaks their build.

The registry is the record

"What did we last publish?" is answered by the package registry, from the spec stored inside the last published package. Git tags are written for convenience and never read back.

Measure what consumers use

Consumers depend on generated code, not on YAML. So Speckify compares the generated packages' public surfaces too, not only the spec.

Fail loudly

A generator that drops an operation, a tool that fails, a type that will not resolve: each stops the run with a clear error rather than passing silently.

Where Speckify sits

Speckify runs inside a producer repository's own GitHub Actions workflow. It reads that repository's spec, talks to two package registries, and drives a set of pinned code generators and analysis tools. Consumers never run Speckify; they install the packages it publishes.

The life of a spec

From the author's point of view there are only two moments: opening a pull request, where Speckify says what version it would publish and why, and merging it, where it publishes.

A spec file under Speckify moves through a small set of states. The only human decision is the merge.

Adopting it

npx speckify init --owner your-org finds openapi*.yaml or openapi*.json files and writes two files. 

# speckify.yaml, beside the code that owns the contract
contracts:
  - name: orders-api
    spec: ./openapi.yaml
    typescript: { package: '@your-org/orders-api', client: true, server: false }
    python: { package: orders-api, client: true, server: true }
publish:
  githubPackages: { owner: your-org }

The second file is .github/workflows/speckify.yml. It has a check job on pull requests and a publish job on pushes to the default branch. Both call Speckify's composite Action directly, pinned to a commit SHA that init resolves at run time. The publish job runs in a release environment, under a concurrency group so two merges cannot publish at once, with only the permissions it needs: contents: write, packages: write and id-token: write.

The publish job lives in the adopter's own file on purpose. PyPI's trusted publishing matches the workflow file that requested the token, and a reusable workflow's token names the reusable workflow instead, so it can never match. Speckify's own reusable workflow is kept for check only.

The Action builds Speckify from its own checkout at that SHA, with pnpm install --frozen-lockfile, so a pinned Action runs exactly that commit's code and fetches no Speckify package at run time.

The plan pipeline

Every check and publish run computes a plan for each contract: its changelog, its bump and its next version. The plan is the heart of Speckify.

Bundle

src/bundle uses @apidevtools/json-schema-ref-parser to inline every external $ref, so the rest of the pipeline always compares one complete document with another. It refuses a $ref that escapes the repository root (symlinks are resolved first) and never fetches a remote $ref. It strips $id and $schema from inlined schemas, which would otherwise confuse the Python model generator, and writes canonical, key-sorted JSON.

Lint

Lint runs before anything else and refuses a spec no generator can turn into working code. Each finding names a JSON pointer.

Rule Why
OpenAPI 3.0.x or 3.1.x only The generators and oasdiff support these.
Every operation has a unique operationId, including after case and separators are ignored createThing and CreateThing both become Python's create_thing; one would silently call the other's endpoint.
No two parameters of one operation collide after normalisation A header Page-Size beside a query page_size renames a Python argument.
No patternProperties Every validator generator tested drops it silently, so the generated server would validate less than the spec says.
No property whose Python name collides with a generated model's own members A property called to_dict breaks every call on that model. The reserved list is derived from the pinned generator itself.

Read the record

src/record asks each registry the contract publishes to for its highest published version, downloads that package, and extracts the openapi.json stored inside it, along with the Speckify version that built it. If a contract's languages have drifted apart because one publish failed, the highest version wins as the baseline.

The version gate

The bump is the highest of four independent judgements:

bump = max(allow-list, oasdiff classification, toolchain impact, client surface)

Why an allow-list

Early designs trusted oasdiff's labels for each change and patched the places where they were missing or wrong. Review kept finding more such places: a keyword oasdiff does not check at some location, a narrowing it labels as a widening, a subtree its allOf flattening drops. A list of known holes can never be shown complete, so the default was inverted. Speckify diffs the two specs itself, and every edit is major unless it matches a short list of shapes known to be safe.

Before diffing, both documents are prepared the same way. Documentation keys are stripped only where they are annotations, so a property that happens to be called title is still data. Every local $ref is inlined where it is used, so a change to a shared component shows up at each place it reaches. Retargeting a $ref leaves a marker, because it renames a generated type.

Direction

The same change can be safe one way and breaking the other. Relaxing maxLength lets a client send more, which is safe; in a response, it means a client can receive something it was not built for.

Where the edit is Direction
Parameters, request bodies request
Response bodies and headers response
Callbacks and webhooks inverted; nothing is allowed there in v1, so any change is major
A component used on both sides judged at every use; minor only if allowed in every direction

Schema rules apply only at plain positions, reached through properties, items, allOf and additionalProperties. Under anyOf, oneOf, not or a conditional, relaxing one part can narrow the whole, so nothing there is allowed.

The allow-list

Rule Direction Why it is safe
operation-added none No existing call can reach it.
optional-parameter-added request Existing calls omit it and stay valid.
request-optional-property-added request Existing bodies omit it and stay valid.
request-constraint-relaxed request Every request valid before is still valid.
parameter-became-optional request Existing calls still send it.
response-optional-property-added response Clients ignore a field they do not know.
response-optional-header-added response Clients ignore a header they do not know.
unreferenced-schema-added none Adds a generated type and changes none.
deprecated-set any An announcement; nothing changes on the wire.

Everything else is major, including any new request constraint, any relaxation in a response, anything under a callback, and any change to servers or security. The full rules and their exact matching are in src/version/allow-list.md.

oasdiff and the classification map

oasdiff 1.32.1 still runs on every plan, always with --flatten-allof; without the flag a breaking change inside an allOf is reported one level too low. Its changes become the changelog, and each is looked up in a committed classification map that covers every one of that release's 755 rules. The map was drafted from oasdiff's source and reviewed row by row. A rule the map does not know counts as major, and a test fails the build if the pinned oasdiff grows a rule the map does not cover. If oasdiff itself fails, the plan stops.

Toolchain impact

A Speckify release can change generated code without any spec change. data/toolchain-impact.json records each release's declared impact on consumers, and the plan compares the Speckify version that built the previous package with the current one.

Comparing the generated code

A spec can change in a way the allow-list judges safe and still break generated code. A new schema named pet beside Pet renames an existing generated type. So every plan with a previous version regenerates both versions with the current toolchain and compares their public surfaces, using each language's own structural model of its symbols. No generated source text is parsed.

TypeScript

Both packages' declaration files load into one TypeScript program, so a single type checker can relate a previous type to a current one. Exports come from checker.getExportsOfModule for each entry point in package.json's exports map. Compatibility uses the checker's own isTypeAssignableTo, so no type rules are reimplemented. Direction comes from use: types reached as parameters are inputs and must accept everything they accepted before; types reached as return values are outputs and must not produce anything new. Zod schemas are compared by z.output<typeof schema>. Any import the checker cannot resolve stops the run, because an unresolved type becomes any and would make every change look compatible.

Python

griffe loads each package statically from its syntax tree. Speckify records modules, public names, parameter kinds and order, and model constructors. Generated models are keyword-only: Speckify overrides one openapi-python-client template to add kw_only=True. So adding a field anywhere in a model cannot break a caller by shifting positional arguments.

Why the server side only reports

The version is judged from the point of view of an existing client. A generated server package is used only by the producer who changed the spec, in the same pull request, so a break there is caught by their own build. Server changes appear in the pull request comment but never raise the version.

What gets generated

Server code is an interface you implement, never stubs you edit. A spec change then shows up as a type error in your service instead of a merge conflict in generated code.

  • TypeScript server. A Handlers interface with one method per operation and a node:http adapter that matches routes, coerces and validates parameters with the zod schemas, and caps JSON bodies at 1 MiB by default. A beforeHandle hook runs before any parsing, so request signatures can be checked first. application/octet-stream bodies are passed through as a stream, never buffered.
  • Python server. A Handlers Protocol with one async method per operation, and create_router(handlers) returning a FastAPI router. It validates parameters and JSON bodies before your handler runs; docs/server-boilerplate.md lists exactly what is and is not checked.
  • Completeness guards. Generators have silently dropped operations before. After generating, Speckify checks that every operationId produced a client function and a handler method, and fails if one is missing.

Publishing and the record

Publishing reconciles each registry with the plan rather than replaying a diff. A target that already has the version is skipped, which makes re-running a failed publish safe.

  • npm packages go to GitHub Packages under the configured owner. GitHub Packages requires the package scope to equal the owner, so Speckify checks that when it loads the config and again just before publishing.
  • Python packages go to PyPI through trusted publishing. The workflow's OIDC identity is exchanged for a short-lived upload credential, so no PyPI token is ever stored.
  • Nothing is overwritten. Registries refuse to republish a version, and Speckify never deletes or force-updates one.

How it is tested

Unit tests that mirror their own implementation prove little, so the suite leans on real tools and on independent checks.

  • Real tools, in CI. The real oasdiff binary, the real generators, a real npm pack and clean install of Speckify, and wheels installed into clean environments. CI runs them; none are skipped.
  • Independent oracles. A property test generates tens of thousands of random edits and checks the gate against a separately written oracle: nothing the oracle calls unsafe may come out below major.
  • Every past bug is a test. Each under-bump found in review is a scenario, run alone and alongside an unrelated harmless change, against both stubbed and real oasdiff.
  • Sabotage. Each control was broken on purpose to see its tests go red, then restored, before it was trusted.

Limits and open work

  • TypeScript and Python only.
  • No standalone JSON Schema contracts yet; JSON Schema is supported inside OpenAPI 3.1 documents.
  • Registries other than GitHub Packages and PyPI are out of scope.
  • Speckify over-bumps by design. Some compatible changes, such as adding a value to an enum used only in requests, currently come out major.
  • Regenerating the previous package with the current toolchain isolates the spec's effect, so a generator upgrade's own effect relies on the toolchain-impact declaration. Nothing yet forces that declaration when a pin moves.
  • Property names built from Unicode lookalike characters can slip past the reserved-name lint.

Open follow-ups are tracked in the project's issues. Contributions are welcome: see CONTRIBUTING.md.
